# Antigravity Rules for Restaurant Orders Project

This file contains strict guidelines and specifications for **Antigravity** and **Antigravity-IDE** agents working on this project. All agents MUST read and adhere to these rules.

---

## 1. General Principles
- **Languages**: Maintain code comments and documentation in Portuguese (PT-BR) unless otherwise specified, as the codebase utilizes Portuguese terms for domain logic (e.g., `estabelecimento`, `garçom`, `pedido`, etc.).
- **Code Modifications**:
  - Do NOT modify existing logic unless specifically requested.
  - Keep changes localized, minimal, and fully compatible with existing modules.
- **Nix Environment**:
  - This project uses **Nix Flakes** for managing dependencies and local services.
  - The shell environment defines Go, Node.js, and helper aliases for Podman/Docker.
  - Always run development commands inside the Nix environment (`nix develop`) if possible.

---

## 2. Backend Guidelines (Go)
- **Architecture**: Modular structure located in [backend/modules](file:///home/doctor/develop/resturant-orders/backend/modules).
  - Every module (except `core`) is completely flattened:
    - **No Sub-Packages**: All route routing (`router.go`), request controllers/handlers (`create.go`, `edit.go`, `select.go`, `delete.go`), GORM database models (`model.go`), and migrations registry (`setup.go`) reside directly in the module's root under the module's own package name (e.g. `package menu`, `package user`).
    - **No nested folders**: There are no subdirectory folders (like `models`, `controllers`, `routes`) within domain modules.
  - **Shared code / Core**:
    - The `core` module contains common infrastructure (DB connection, global routing, responses, SSE broker, standard error handlers) and must not be flattened.
    - **Middleware**: To prevent circular imports between flattened modules (e.g. when `auth` imports `user` for the User model and `user` imports `auth` for authentication middleware), the JWT token builder and authentication middleware are placed in [backend/modules/core/middleware](file:///home/doctor/develop/resturant-orders/backend/modules/core/middleware).
- **Frameworks**:
  - HTTP Server: **Gin Gonic** (`github.com/gin-gonic/gin`).
  - ORM: **GORM** (`gorm.io/gorm`) with PostgreSQL.
- **Database & Migrations**:
  - Custom PostgreSQL enums (e.g., `order_status`, `role_type`) must be created via [infra/enums.sql](file:///home/doctor/develop/resturant-orders/infra/enums.sql) before GORM's `AutoMigrate` runs.
  - Custom schemas/migrations are registered using the core database migrator registry.
- **SSE (Server-Sent Events)**:
  - Real-time communication is managed via SSE in the kitchen module (`StreamKitchenEvents`) and core services broker (`services.Br`). Keep SSE connections clean, handle client disconnection, and prevent resource leaks.
- **Error Handling & Database Access**:
  - Use `core.DB` (found in `modules/core/module.go`) for GORM database query executions.
  - Use `standard.NewReponse().Error(c)` (found in `modules/core/standard`) for unified HTTP error responses.
  - Log errors using `slog` JSON format (configured in `core`).

---

## 3. Frontend Guidelines (Next.js + Tailwind CSS)
- **Framework**: **Next.js 16** (App Router) with React 19.
- **Styling**: **Tailwind CSS v4** (with `@import "tailwindcss"` in `globals.css`).
  - Do not use Tailwind configuration files unless explicitly required; v4 utilizes CSS-based configuration.
- **State Management**: **Redux Toolkit** and **Redux Persist** (using `<StoreProvider>` in the App root).
- **API Clients**: Use **Axios** pointing to `NEXT_PUBLIC_API_URL` (usually `http://localhost:8080`).

---

## 4. Development & Infrastructure Operations
- Always manage PostgreSQL and other infrastructure services using the defined Nix aliases:
  - `pg-start` / `pg-stop` to manage local database storage.
  - `testar-dev` / `stop-dev` to spin up local docker-compose environments (Podman).
  - `testar-prod` / `stop-prod` to run production-like validation.
